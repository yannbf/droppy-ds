# ScrollArea

{/* BEGIN: general */}

A scrollable panel with a themed scrollbar in place of the platform's own.

```tsx
import { ScrollArea } from '@droppy/design-system'
```

<Canvas of={ScrollAreaStories.Default} />

## Features

- **Replaces the platform scrollbar** with a themed track and thumb, so long content stays consistent across operating systems and browsers.
- **The scrollbar reveals itself on hover or while scrolling**, staying out of the way otherwise.
- **Native scroll mechanics throughout** — wheel, touch, keyboard, and thumb drag all work as the platform expects; only the scrollbar's appearance changes.
- **`orientation` picks which axes get a scrollbar** — `'vertical'` (default), `'horizontal'`, or `'both'`, which also renders the corner where the two tracks would otherwise intersect.

{/* END: general */}

{/* BEGIN: when-to-use */}

## When to use

- A fixed-size panel — a card, a comment list, a table of options — whose content can run longer than the space available, without wanting to grow the layout around it.

## When not to use

- For the page itself, rely on native document scrolling — `ScrollArea` is for a panel embedded within the page, not the page's own scroll.

{/* END: when-to-use */}

{/* BEGIN: behavior */}

## How it works

Scrollbars are only mounted once the content actually overflows, and only on the axes
`orientation` asks for. With `both`, a corner part fills the square where the two tracks would
otherwise intersect.

## Do's and don'ts

### Do

- Give the `ScrollArea` a bounded height through `className`, so it has something to scroll
- Match `orientation` to the axis the content actually overflows on; `both` renders two scrollbars
  and the corner between them
- Keep focusable content inside the region, e.g. links or controls, so keyboard users can reach
  what sits below the fold

### Don't

- Don't rely on the scrollbar to signal there is more: it is revealed on hover and scroll, so the
  content itself has to hint at the overflow
- Avoid nesting one `ScrollArea` inside another; this complicates user interaction

{/* END: do-dont */}

{/* BEGIN: a11y */}

## Keyboard & screen reader

| Key / interaction                                   | Action                                                                          |
| --------------------------------------------------- | ------------------------------------------------------------------------------- |
| Arrow keys / Page Up / Page Down (viewport focused) | Scrolls the content                                                             |
| Tab                                                 | Scrollbar thumb is not part of tab order — scroll the viewport directly instead |

- **ARIA:** none of the parts carry a role beyond the plain `<div>` Base UI renders — a scroll area is a layout affordance, not a distinct landmark.
- **Screen reader:** reads the content inside as it would any other block; the scrollbar itself is not announced.

## Styling

Colors, track/thumb sizing, and the hover/scroll-gated opacity come entirely from the theme layer's `ScrollArea*` classes. `className` merges onto the root, so it composes with the theme rather than replacing it.

## Known issues & open questions

- [#236](https://github.com/yannbf/droppy-ds/issues/236): inline children are split into vertically stacked flex items with 1rem gaps. **Workaround:** wrap the content in a single block element (e.g. one div) so it becomes a single flex item with normal inline flow.
- [#237](https://github.com/yannbf/droppy-ds/issues/237): orientation="both": corner square stays visible while scrollbars fade and permanently blocks clicks. **Workaround:** app CSS on the global .ScrollAreaCorner class can add the missing opacity/pointer-events gating or make the corner inert.
- [#238](https://github.com/yannbf/droppy-ds/issues/238): orientation only limits which scrollbars render — off-axis overflow stays scrollable with no visual affordance. **Workaround:** pass orientation="both" when horizontal overflow is possible, or clamp overflow-x on .ScrollAreaViewport with !important app CSS.
- [#239](https://github.com/yannbf/droppy-ds/issues/239): scrollbar DOM is absent on first paint and never renders in jsdom; keepMounted is not exposed. **Workaround:** assert on scrollbars only in real-browser test envs inside waitFor and target the always-present viewport in jsdom; keepMounted itself is unreachable.
- [#240](https://github.com/yannbf/droppy-ds/issues/240): root paints an opaque surface-page background, producing a mismatched patch on card surfaces. **Workaround:** override the root background via className/app CSS to transparent or the surrounding surface token.
- [#241](https://github.com/yannbf/droppy-ds/issues/241): docs claim no part carries a role, but Root/Viewport/Content render role="presentation" and the focusable viewport trips axe. **Workaround:** allowlist axe's presentation-role-conflict rule for the viewport in CI; the rendered attributes themselves cannot be changed.
- [#242](https://github.com/yannbf/droppy-ds/issues/242): RTL: content clearance uses physical padding while the scrollbar is positioned with logical properties. **Workaround:** swap the content padding sides under [dir='rtl'] in app CSS and wrap the app in Base UI's DirectionProvider.
- [#243](https://github.com/yannbf/droppy-ds/issues/243): switching orientation at runtime leaves stale scrollbar geometry. **Workaround:** remount on change with key=&#123;orientation&#125;, at the cost of losing scroll position.
- [#244](https://github.com/yannbf/droppy-ds/issues/244): theme ships a ScrollAreaViewportFade variant no component can apply. **Workaround:** replicate the fade in app CSS targeting .ScrollAreaViewport, where Base UI sets the overflow variables.
- [#125](https://github.com/yannbf/droppy-ds/issues/125): the prop type is a closed set, so `id`/`data-testid`/`aria-*`/`style`/event handlers never reach the rendered DOM.
