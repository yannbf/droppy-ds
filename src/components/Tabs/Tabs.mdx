# Tabs

{/* BEGIN: general */}

A set of panels, one visible at a time, switched by a row of tab buttons — settings sections, a
profile's sub-views, anything reviewed one part at a time rather than all at once.

```tsx
import { Tabs } from '@droppy/design-system'
```

<Canvas of={TabsStories.Default} />

## Features

- **`tabs` covers the common case**: an array of `{ value, label, content, disabled? }` renders
  the whole tablist and its panels — no need to compose `Tabs.Tab`/`Panel` by hand.
- **Renders the theme's `Indicator`**, an animated highlight that slides beneath the active tab.
- **`value`/`defaultValue`/`onValueChange` passthrough**, for a controlled set of tabs driven by
  state outside the component.
- **Activates on click**, not on focus alone — arrow-keying through the tabs moves focus without
  changing which panel is shown, matching
  [WCAG 2.5.2 Pointer Cancellation](https://www.w3.org/WAI/WCAG21/Understanding/pointer-cancellation.html).

{/* END: general */}

{/* BEGIN: when-to-use */}

## When to use

- Content split into a small number of named sections where only one is relevant at a time — a
  settings page, an item's details vs. reviews, a dashboard's stat groupings.

## When not to use

- For a sequence the user is meant to complete in order, like a checkout or a wizard, use explicit
  "next"/"back" navigation instead — tabs imply free jumping between sections, not a required
  order.
- For content that benefits from being scanned all at once rather than switched between, don't
  hide it behind tabs — an [Accordion](?path=/docs/layout-structure-accordion--docs) at least keeps
  every section's title visible, and plain layout keeps everything visible outright.

{/* END: when-to-use */}

{/* BEGIN: behavior */}

## How it works

### Focus does not activate

Tabs activate on click, not on focus: arrowing along the row moves focus without swapping the
panel, so a keyboard user can read the labels before committing. Only Enter, Space, or a click
activates.

<Canvas of={TabsStories.FocusDoesNotActivate} />

### Controlled value

`value` with `onValueChange` hands the active tab to the caller's state. One without the other
leaves the row stuck — the callback fires, the tab never moves.

<Canvas of={TabsStories.ControlledValue} />

### The sliding indicator

`Tabs.Indicator` writes the active tab's measured position and size to CSS custom properties,
which the theme transitions on top of.

<Canvas of={TabsStories.AnimatedIndicator} />

## Anatomy

A tab row with its indicator, and one panel per tab. The list is flat — `tabs` renders the whole set, so there is no `Tabs.Tab`/`Tabs.Panel` to compose by hand.

<Canvas of={TabsStories.Anatomy} />

| Part      | `data-part` | Renders    | Purpose                                                                  |
| :-------- | :---------- | :--------- | :----------------------------------------------------------------------- |
| Root      | `root`      | `<div>`    | Owns the active value and links tabs to panels                           |
| List      | `list`      | `<div>`    | The `role="tablist"` row                                                 |
| Tab       | `tab`       | `<button>` | One per entry, carrying `aria-selected`                                  |
| Indicator | `indicator` | `<span>`   | The sliding underline; writes the active tab's position as CSS variables |
| Viewport  | `viewport`  | `<div>`    | Wraps the panels                                                         |
| Panel     | `panel`     | `<div>`    | One per tab; only the active one shows                                   |

## Do's and don'ts

### Do

- Use `Tabs` for peer views of one subject the reader can jump between freely.

### Don't

- Avoid `Tabs` for a sequence meant to be completed in order — a checkout, a wizard. Tabs invite
  jumping; use explicit next/back navigation instead.
- Avoid hiding content behind `Tabs` that's better scanned all at once —
  [Accordion](?path=/docs/layout-structure-accordion--docs) keeps every title visible, and plain
  layout shows everything.

{/* END: do-dont */}

{/* BEGIN: a11y */}

## Keyboard & screen reader

| Key / interaction | Context            | Action                                                            |
| ----------------- | ------------------ | ----------------------------------------------------------------- |
| Tab               | outside tablist    | Moves focus into the tablist, landing on the active tab           |
| Left/Right arrow  | horizontal tablist | Moves focus between tabs, wrapping at the ends; does not activate |
| Up/Down arrow     | vertical tablist   | Same as above, on the vertical axis                               |
| Enter / Space     | focused tab        | Activates the focused tab, showing its panel                      |
| Click             | any tab            | Activates that tab immediately                                    |

- **ARIA:** the tab row carries `role="tablist"`; each tab is `role="tab"` with `aria-selected`
  and `aria-controls` pointing at its panel; each panel is `role="tabpanel"` with
  `aria-labelledby` pointing back at its tab.
- **Screen reader:** announces the tablist, each tab's selected state, and each panel as
  associated with its tab.
- **You must provide:** a meaningful `label` per tab — it becomes both the visible tab text and
  its accessible name.

## Styling

Droppy's own stylesheet carries no rules for `Tabs` — the theme layer's `TabsRoot`, `TabsList`,
`TabsTab`, `TabsIndicator`, `TabsPanelViewport`, and `TabsPanel` classes cover the layout, active
state, and indicator animation in full.

`className` merges onto the root, so it composes with the theme layer rather than replacing it.

## Decision log

- **2026-07**: Droppy's Tabs took a data-driven `tabs: {value, label, content}[]` array instead of exposing the underlying compound-component composition, keeping call sites declarative ([additional components commit](https://github.com/yannbf/droppy-ds/commit/1fba4ce05fa71da8aa51a56ea60dae6b218c1868)).
- **Built on Base UI [`Tabs`](https://base-ui.com/react/components/tabs).** Droppy supplies the props, the theme classes, and the copy around it.

## Known issues & open questions

- [#245](https://github.com/yannbf/droppy-ds/issues/245): inactive panels unmount on every switch, destroying all state in tab content; keepMounted is not exposed. **Workaround:** lift state out of tab content into the parent or a store — keepMounted itself is unreachable through this wrapper.
- [#246](https://github.com/yannbf/droppy-ds/issues/246): theme caps the root at max-width: 20rem and the tab row can neither wrap nor scroll — realistic labels overflow past the panel border. **Workaround:** override max-width and add overflow handling from app CSS via className plus the global part classes.
- [#247](https://github.com/yannbf/droppy-ds/issues/247): omitting defaultValue renders no selected tab on the server/first render, then onValueChange fires by itself on mount. **Workaround:** always pass defaultValue (or fully control value) so a tab is selected from the first render and no mount callback fires.
- [#248](https://github.com/yannbf/droppy-ds/issues/248): onValueChange is typed (value: string) =&gt; void but is invoked with null, with values the user never picked, and with a hidden second argument. **Workaround:** wrap the callback with explicit arity and treat the value as string | null; keep the active tab from being removed/disabled.
- [#249](https://github.com/yannbf/droppy-ds/issues/249): controlled value that matches no tab renders a fully blank component with no warning. **Workaround:** validate the controlled value against the tabs array before passing it, falling back to a known tab.
- [#250](https://github.com/yannbf/droppy-ds/issues/250): the tablist can never be given an accessible name — no prop reaches the role="tablist" element. **Workaround:** set aria-label on the rendered tablist from a wrapper ref in an effect (unmanaged DOM patch).
- [#251](https://github.com/yannbf/droppy-ds/issues/251): docs and theme advertise vertical orientation, but there is no orientation prop — vertical mode is unreachable. **Workaround:** compose Base UI Tabs.Root orientation="vertical" directly, reusing the shipped global theme class names.
- [#252](https://github.com/yannbf/droppy-ds/issues/252): docs claim every tab carries aria-controls pointing at its panel, but only the active tab does. **Workaround:** test against actual behavior — assert aria-controls on the active tab only and inactive panels as absent.
- [#253](https://github.com/yannbf/droppy-ds/issues/253): docs claim Droppy's stylesheet carries no Tabs rules, but .droppy-Tabs pins font-family — an app's own font never reaches tab text. **Workaround:** restore the app font with a higher-specificity rule such as .my-tabs.droppy-Tabs &#123; font-family: inherit &#125;.
- [#125](https://github.com/yannbf/droppy-ds/issues/125): the prop type is a closed set, so `id`/`data-testid`/`aria-*`/`style`/event handlers never reach the rendered DOM.
