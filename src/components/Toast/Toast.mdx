# Toast

{/* BEGIN: general */}

A stack of transient, self-dismissing notifications for things the reader doesn't need to act on right away.

```tsx
import { ToastProvider, useToast } from '@droppy/design-system'
```

<Canvas of={ToastStories.Default} />

## Features

- **No markup to write per toast.** `ToastProvider` renders the viewport and the toast list for you — call `useToast().add(...)` from anywhere beneath it and a toast appears.
- **Auto-dismisses on a timer**, and stacks newest-first when more than one is visible at once.
- **Announced to screen readers** through the viewport's live region, without stealing focus on open.
- **Portals to `document.body`** by default, so a parent's `overflow: hidden` or stacking context can't clip it. `container` retargets the portal, matching [Modal](?path=/docs/overlays-modal--docs)'s prop of the same name.

{/* END: general */}

{/* BEGIN: when-to-use */}

## When to use

- A confirmation of something that already happened — a draft saved, a file archived, an export finished — that the reader doesn't need to dismiss to keep working.
- A transient status message like "Copied," which [Tooltip](?path=/docs/overlays-tooltip--docs) explicitly can't provide, since a tooltip's content is never announced to screen readers.

## When not to use

- A decision the reader must make before continuing — use [Modal](?path=/docs/overlays-modal--docs) instead, which blocks the page and traps focus until it's answered.
- Content the reader must be able to reach at their own pace rather than within a timeout — put it on the page instead.

{/* END: when-to-use */}

{/* BEGIN: behavior */}

## How it works

### The close affordance

The close button is `aria-hidden` until the stack is hovered or focused, so a single passing
notification doesn't compete with the page for keyboard attention.

<Canvas of={ToastStories.CloseAppearsOnHover} />

### Enter and exit motion

Each toast enters and leaves off `[data-starting-style]` and `[data-ending-style]`, and the exit
additionally reads `[data-swipe-direction]` so a swiped toast leaves the way it was pushed rather
than fading in place.

## Do's and don'ts

### Do

- Wrap the app once in `ToastProvider` at the root, and raise toasts through `useToast().add(...)`
  from anywhere beneath it
- Reach for `promise` to chain an async task's loading state through to success or failure, so one
  toast tells the whole story

### Don't

- Don't leave the only record of something in a toast: it dismisses itself, and cannot be reopened after the fact
- Avoid raising several toasts for one action; `limit` marks older ones as limited rather than
  dropping them, so the stack still fills

{/* END: do-dont */}

{/* BEGIN: a11y */}

## Keyboard & screen reader

| Key / interaction          | Context            | Action                                         |
| -------------------------- | ------------------ | ---------------------------------------------- |
| F6                         | anywhere           | Jumps focus to the toast stack                 |
| Tab (from the stack)       | open               | Enters the stack at the newest toast           |
| Escape                     | a toast is focused | Closes that toast; focus moves to the next one |
| Shift+Tab (from the stack) | open               | Returns focus to wherever it was before        |

- **ARIA:** the viewport is a live region so a new toast is announced without moving focus; each toast is announced according to its priority.
- **Screen reader:** hears the toast's title and description as it appears, and can reach its `Dismiss` button by tabbing into the stack.
- **You must provide:** a `title` or `description` on every toast that carries the information the reader needs — the toast itself supplies no default text.

## Styling

Colors, spacing, and the stacking/swipe transforms come entirely from the theme layer's `Toast*` classes. `className` on `ToastProvider` merges onto the viewport, so it composes with the theme rather than replacing it.

## Decision log

- **2026-07**: Toast shipped provider-only: it has no trigger and no `open` prop — an app wraps its tree once in ToastProvider and raises toasts imperatively through `useToast().add()`, with the provider owning the only rendering of the toast list; it reuses the same element-or-selector `container` prop as Modal and Sidebar, with `timeout` and `limit` as the tuning knobs ([additional components commit](https://github.com/yannbf/droppy-ds/commit/1fba4ce05fa71da8aa51a56ea60dae6b218c1868), [Toast.tsx](https://github.com/yannbf/droppy-ds/blob/main/src/components/Toast/Toast.tsx)).
- **2026-07**: because Mealdrop has no status system beyond `text.error`, toast success/info/warning inks were collapsed to `text.primary` as a neutral-first gap fill; proper status surface/ink tokens (success/danger/warning/info surface + on-surface pairs) were identified as the missing piece but deliberately left for the system owner to decide rather than invented during extraction.
- **Built on Base UI [`Toast`](https://base-ui.com/react/components/toast).** Droppy supplies the props, the theme classes, and the copy around it.

## Known issues & open questions

- [#185](https://github.com/yannbf/droppy-ds/issues/185): viewport z-index: 1 renders toasts behind Modal, Sidebar, and other design-system overlays. **Workaround:** raise the viewport's z-index from app CSS via the stable droppy-Toast class (e.g. .droppy-Toast.droppy-Toast &#123; z-index: 100 &#125;) or a className on ToastProvider.
- [#190](https://github.com/yannbf/droppy-ds/issues/190): add() options actionProps and positionerProps are accepted by the types but silently ignored — action onClick handlers are swallowed. **Workaround:** embed the action button in the description ReactNode (it stays clickable); no workaround for anchored positioning — do not pass positionerProps.
- [#194](https://github.com/yannbf/droppy-ds/issues/194): 'Dismiss' button text and 'Notifications' region label are hardcoded English with no localization path. **Workaround** (partial): the region's aria-label can be patched post-mount via a DOM effect on .droppy-Toast; the visible 'Dismiss' label has no workaround.
- [#198](https://github.com/yannbf/droppy-ds/issues/198): A toast raised while the window is unfocused starts its auto-dismiss timer anyway and can disappear unseen. **Workaround:** gate the per-toast timeout on document.hasFocus() at add time (timeout: document.hasFocus() ? undefined : 0).
- [#201](https://github.com/yannbf/droppy-ds/issues/201): timeout/limit defaults (5000 ms, 3) are undocumented, and hidden 'limited' toasts keep their dismiss timers running contrary to the docs. **Workaround:** pass explicit limit/timeout sized to the worst-case burst (or timeout=&#123;0&#125;), and coalesce repeat notifications with add(&#123; id &#125;) upserts.
- [#205](https://github.com/yannbf/droppy-ds/issues/205): timeout=&#123;Infinity&#125; (or any value &gt;= 2^31 ms) dismisses toasts almost instantly instead of never. **Workaround:** use the documented timeout=&#123;0&#125; / add(&#123; timeout: 0 &#125;) for persistent toasts; never pass Infinity or values &gt;= 2^31.
- [#207](https://github.com/yannbf/droppy-ds/issues/207): limit=&#123;0&#125; silently hides every toast instead of meaning 'no limit'. **Workaround:** never pass limit=&#123;0&#125; or negative; omit the prop or pass a large finite number for 'unlimited'.
- [#208](https://github.com/yannbf/droppy-ds/issues/208): no way to raise toasts from outside the React tree — Base UI's toastManager/createToastManager escape hatch is not exposed. **Workaround:** a bridge component inside ToastProvider stores useToast() in a module-level ref for non-React callers.
- [#211](https://github.com/yannbf/droppy-ds/issues/211): useToast().promise() re-rejects its returned promise, so the fire-and-forget usage the docs suggest produces unhandled promise rejections on failure. **Workaround:** always await in try/catch or append .catch(() =&gt; &#123;&#125;); race never-settling promises with a timeout.
- [#213](https://github.com/yannbf/droppy-ds/issues/213): every component calling useToast() re-renders on every toast lifecycle event app-wide. **Workaround:** capture the stable manager methods once in a bridge and distribute them via your own context/ref; React.memo contains the rest.
