# Choosing components

A handful of Droppy's components solve seemingly overlapping problems, and you may find it
hard to decide which component is the best fit for your use case. This page compares key
characteristics of similar components to help you choose the right one.

## Actions and navigation: Button, IconButton, Link

These controls render as clickable text or an icon. They differ in what happens on
activation, and in whether they follow the page's theme.

|                      | Button                      | IconButton                          | Link                       |
| -------------------- | --------------------------- | ----------------------------------- | -------------------------- |
| Element              | `<button>`                  | `<button>`                          | `<a>`                      |
| Effect               | in-page action              | in-page action                      | navigates: changes the URL |
| Label                | visible text, optional icon | icon only, `aria-label` required    | inline text                |
| Follows `data-theme` | yes                         | **no**: fixed light pill, by design | yes                        |

[Button](?path=/docs/actions-button--docs) is the default: primary and secondary actions,
with `clear`, `round`, and `large` variants plus an `icon` slot. It always renders a real
`<button>`, so it can cover icon-only affordances too (`round`, `clear`, `icon`, no children),
in which case the same `aria-label` requirement applies.

[IconButton](?path=/docs/actions-iconbutton--docs) exists for use on top of arbitrary imagery, where
it would be more complicated to guarantee contrast if we allowed theming. That's why [IconButton](?path=/docs/actions-iconbutton--docs)
is always light with a dark icon. It must always have an `aria-label` attribute to be accessible.

[Link](?path=/docs/actions-link--docs) is for navigation: it renders a plain `<a href>` (or
a router element via `render`). It's important you use [Link](?path=/docs/actions-link--docs) rather
than a button for navigation: it makes links more perceivable for users and provides support for right
click and opening in new tabs.

## Typography: Body vs Heading

Droppy provides two text components, [Body](?path=/docs/typography-body--docs) and
[Heading](?path=/docs/typography-heading--docs). They don't differ just in visual style.
[Heading](?path=/docs/typography-heading--docs) renders a real `<h1>`-`<h5>` element,
which screenreader users use to navigate the page, whereas [Body](?path=/docs/typography-body--docs)
carries a neutral semantic.

## Providing a value: Input, Select, NumberField, QuantityStepper

These controls collect a single value in a form. Work through them in order:

1. Free-form text? →
   [Input](?path=/docs/forms-input-input--docs): a labelled text field with a reserved error slot.
2. One value out of a short, known list? → [Select](?path=/docs/forms-input-select--docs): a
   native `<select>` or mobile platform picker.
3. An arbitrarily large number? →
   [NumberField](?path=/docs/forms-input-numberfield--docs): typeable, with increment/decrement
   buttons and a drag-to-scrub label.
4. A small, bounded count that's often close to 1?
   → [QuantityStepper](?path=/docs/forms-input-quantitystepper--docs): two buttons and a
   live-announced value, no typing at all.

Once a job has its component, every screen uses the same one. If the cart line and the
add-to-cart dialog both set an item's quantity, they use the same control — the answer to the
questions above doesn't change between screens, so neither should the component.

## Progressive disclosure: Accordion, Tooltip, Tabs

These components hide content until something asks for it, but differ wildly in when they're appropriate to.

|                            | Tooltip                                   | Accordion                         | Tabs                              |
| -------------------------- | ----------------------------------------- | --------------------------------- | --------------------------------- |
| Opens on                   | hover / focus                             | click                             | click                             |
| Content                    | a hint, never essential and small in size | a full section, can be essential  | a full panel, can be essential    |
| Stays open                 | no                                        | yes                               | yes, until another tab is picked  |
| Shown on touch             | no                                        | yes                               | yes                               |
| Peer headings stay visible | n/a                                       | yes, every header stays on screen | no, only the active panel renders |

[Tooltip](?path=/docs/overlays-tooltip--docs) should only be used for very small pieces of
content that are situationally useful but not essential. Its content is invisible to touch
and assistive-tech users by design. A tooltip's content can never be interactive.

[Accordion](?path=/docs/layout-structure-accordion--docs) exposes sections of content that
behave as a coherent set. The content can be short or long, and each heading of the accordion
is visible whether sections are open or not.

[Tabs](?path=/docs/navigation-tabs--docs) looks similar (one region visible among peers) but
only the active panel exists on screen, and its trigger row is built for fast switching rather
than scanning. It also works better when the content of each panel has a similar size.

## Interruptions and messages: Toast, Sidebar, Modal, ErrorBlock

These components tell the user something happened or ask them to act, differing on whether the
page keeps running behind them and whether a response is required.

|                         | Toast           | ErrorBlock | Sidebar | Modal     |
| ----------------------- | --------------- | ---------- | ------- | --------- |
| Blocks until a response | no              | no         | yes     | yes       |
| Self dismisses          | yes, on a timer | no         | no      | no        |
| Disruptiveness          | low             | high       | medium  | very high |

[Toast](?path=/docs/feedback-status-toast--docs) is for something that already happened and needs
no response. It has no trigger part of its own: you call `useToast().add(...)` from anywhere
beneath `ToastProvider` and a toast appears, dismissing itself on a timer.

[ErrorBlock](?path=/docs/feedback-status-errorblock--docs) interrupts the user's attention and
train of thought, rather than their ability to interact. It renders in the page's normal flow
and communicates information that likely warrants user attention: an empty search,
a 404, a failed request, ideally paired with one recovery action.

[Sidebar](?path=/docs/overlays-sidebar--docs) and [Modal](?path=/docs/overlays-modal--docs)
share the same overlay mechanics (focus trap, scroll lock, Escape and outside-press dismissal)
so they may feel interchangeable. Modal takes over the page for a single decision ("Remove from cart?")
and feels very disruptive, whereas Sidebar shares space in the page and provides additional
actions and information in context.

## Loading feedback: Spinner, Skeleton, Progress, ProgressBar

These components cover all situations where users must wait.

|                     | Skeleton       | Spinner                       | Progress                   | ProgressBar                    |
| ------------------- | -------------- | ----------------------------- | -------------------------- | ------------------------------ |
| Stands in for       | a known layout | nothing (no shape to preview) | a numeric task             | a numeric task                 |
| Indeterminate       | always         | always                        | opt-in with `value={null}` | no, a `value` is required      |
| Label / Value parts | n/a            | `label` only                  | built in                   | caller renders them separately |

[Skeleton](?path=/docs/feedback-status-skeleton--docs) must match the shape it's standing in for:
a card, a list row, a line of text, etc. Its goal is to reduce perceived wait duration, but it should
not cause jumps in the page layout.

In contrast, [Spinner](?path=/docs/feedback-status-spinner--docs) can be used when the eventually
displayed layout is unpredictable and cannot be represented with skeletons.

When the duration of the wait is known (e.g. a delivery arrival time), reach for
[Progress](?path=/docs/feedback-status-progress--docs) or
[ProgressBar](?path=/docs/feedback-status-progressbar--docs). Progress has built-in `Label`/`Value` parts and an
indeterminate mode for when the length turns out to be unknown mid-task (e.g. the delivery driver stopped moving).
ProgressBar is a more compact and bare-bones sibling: `value` is required, there's no indeterminate state or
built-in label and value. It's easier to embed in dense UIs like on DropBoard.

## Page structure: Container, PageSection, Card

These components wrap page content, and together they compose a content hierarchy.

|                | Container                | PageSection                    | Card                           |
| -------------- | ------------------------ | ------------------------------ | ------------------------------ |
| Width          | capped at 1600px         | capped at 1600px               | intrinsic to its parent        |
| Visual surface | none                     | none                           | background + radius + clipping |
| Heading slot   | none                     | title + optional action button | none, caller composes          |
| Typical unit   | the whole content column | one row/section within it      | one tile within a section      |

[Container](?path=/docs/layout-structure-container--docs) is the plain bound: it has background or heading,
and only implements max-width and responsive padding.

[PageSection](?path=/docs/layout-structure-pagesection--docs) is similar, but adds a title
and an optional "view all" action. It structures large areas of content within a Container.

[Card](?path=/docs/media-content-card--docs) is the next smallest unit of content. It has a
visual surface and contains one snippet of content, usually inside a collection.
