# Accessibility guidelines

<Meta title="Accessibility guidelines" tags={['general-a11y']} />

Web accessibility is not only a legal requirement in many jurisdictions, but also a moral imperative and a business advantage. It ensures that all users, regardless of context, can access and interact with digital content effectively. By adhering to accessibility guidelines, we create inclusive experiences that benefit everyone, including those with temporary or situational impairments.

Droppy builds its accessibility compliance on top of Base UI, which itself implements trusted accessibility patterns. Droppy's theme ensures components are perceivable, operable and understandable. As an app developer, you too contribute to accessibility compliance, by correctly handling page heading structure, landmark order, labels and alt text for content, etc.

## Standards & targets

All our products, and so, all Droppy components, must meet **WCAG 2.2 Level AA** success criteria.

### Target audience

We support a wide range of users with their own needs:

- **Keyboard-only** users, who need a visible focus indicator and a predictable tab order
- **Screen-reader** users, who depend on correct HTML semantics
- **Low-vision** users, who rely on contrast improvement and magnification tools
- **Motor-impaired** users, who need targets sized and spaced for imprecise pointing
- **Reduced-motion** users, for whom animation is a vestibular or attentional hazard

### Manual testing stack

We aim to be compatible with the NVDA and VoiceOver screen readers, which are both free and available to the vast majority of our B2B and B2C users. NVDA is available on Windows, and VoiceOver on macOS. Support for High Contrast Mode and magnification tools should be tested on Windows and macOS, with Chrome and Safari.

We use those tools to test Droppy components in isolation. We encourage you to also use them on MealDrop and DropBoard app pages to verify that Droppy components are integrated correctly.

### Automated testing stack

`@storybook/addon-a11y` runs on every story in Droppy, as a first line of defense against WCAG violations.
It uses axe-core to automatically detect patterns that are likely to be violations. In rare cases,
the addon reports false positives. For instance, [Carousel](?path=/docs/media-content-carousel--docs) intentionally dims its non-interactive slide previews, which triggers a `color-contrast` violation. We disable axe-core rules in such cases, so that you can rely on the addon's violation reports to confirm the presence of actual accessibility violations.

Additionally, we write `play` functions that are run in Vitest via `@storybook/addon-vitest`. In these `play`
function tests, we verify additional requirements, such as:
* the keyboard tab order is as expected, and focus traps resolve as expected
* the expected ARIA attributes show up based on the passed props
* the expected `aria-live` announcements are made when a component's state changes
* etc.

## WCAG compliance FAQ

### Contrast

Our theme's color palette is designed to meet the following minimum contrast ratios for text and UI elements, ensuring readability and accessibility for users with visual impairments. Below is a reminder of the minimum contrast ratios mandated by WCAG 2.2 AA:

| Content                                     | Minimum ratio |
| :------------------------------------------ | :------------ |
| Normal text                                 | 4.5:1         |
| Large text (≥24px, or ≥19px bold)           | 3:1           |
| UI component boundaries & graphical objects | 3:1           |

### Focus outlines

Our theme includes a visible focus outline for interactive elements, ensuring that keyboard users can easily track focus. The focus outline is applied using the `:focus-visible` pseudo-class, and its appearance is consistent across all components. We use a double shadow to make it easier for you to achieve contrast ratio regardless of the background color. Always use the Droppy focus outline to stay safe.

### Touch target sizing

We ensure that all interactive elements meet the minimum touch target size of 48×48 CSS pixels, as recommended by WCAG 2.2. This sizing accommodates users with motor impairments and those using touch devices, providing a comfortable and accessible interaction experience. For instance, [Button](?path=/docs/actions-button--docs) and [IconButton](?path=/docs/actions-iconbutton--docs) components have a default size of 64×64 CSS pixels, and a `small` variant size of 48×48 CSS pixels.

### Reduced motion

Droppy currently does not handle reduced motion for you. It is your responsibility, in app code, to apply the `prefers-reduced-motion` media query to any motion you layer on top of Droppy components.

## Keyboard navigation of composite components

Every Droppy composite component is built on a Base UI composite primitive, or on a small number of ordinary HTML elements. Simple components use single Tab stops, but composite components have more complex keyboard navigation models that must match WCAG Authoring Practice Guidelines to be predictable for keyboard and screenreader users. The table below summarizes the keyboard navigation model for each Droppy composite component.


| Component                                                        | Built on                                         | Model                                                                                                                                                                                                                                              |
| :--------------------------------------------------------------- | :----------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Tabs](?path=/docs/navigation-tabs--docs)                        | `@base-ui/react/tabs`                            | One Tab stop for the tablist; arrow keys move a roving highlight and wrap at the ends. A separate activation — click, Enter, or Space — selects; arrow-key focus alone doesn't.                                                                    |
| [Accordion](?path=/docs/layout-structure-accordion--docs)        | `@base-ui/react/accordion`                       | No roving focus, matching Base UI's own alignment with the current WAI-ARIA APG accordion pattern. Every trigger is its own ordinary Tab stop; Enter/Space toggles it.                                                                             |
| [Modal](?path=/docs/overlays-modal--docs)                        | `@base-ui/react/dialog`                          | Focus-trapped popup: Tab/Shift+Tab loop inside it rather than escaping to the page. Escape closes.                                                                                                                                                 |
| [Sidebar](?path=/docs/overlays-sidebar--docs)                    | `@base-ui/react/drawer`                          | Same focus-trap model as Modal. Swipe-to-dismiss is pointer-only, so Escape and the visible close button are the keyboard equivalents.                                                                                                             |
| [Toast](?path=/docs/feedback-status-toast--docs)                 | `@base-ui/react/toast`                           | Outside the page's tab order until summoned: F6 jumps focus to the stack, Tab enters at the newest toast, Escape dismisses the focused one.                                                                                                        |
| [Tooltip](?path=/docs/overlays-tooltip--docs)                    | `@base-ui/react/tooltip`                         | Opens on trigger focus with no delay, closes on blur or Escape. Carries no ARIA relationship to the trigger, so the trigger needs its own accessible name regardless.                                                                              |
| [NumberField](?path=/docs/forms-input-numberfield--docs)         | `@base-ui/react/number-field`                    | Up/Down arrow steps the value; Home/End jump to `min`/`max` when set; typing replaces it directly.                                                                                                                                                 |
| [ScrollArea](?path=/docs/layout-structure-scrollarea--docs)      | `@base-ui/react/scroll-area`                     | Arrow keys and Page Up/Down scroll the focused viewport; the scrollbar thumb itself is never a Tab stop.                                                                                                                                           |
| [Select](?path=/docs/forms-input-select--docs)                   | Native `<select>` — no Base UI primitive         | The platform's own picker rather than a scripted listbox: Up/Down/Home/End and native typeahead once open, Enter/Escape to commit or cancel.                                                                                                       |
| [Carousel](?path=/docs/media-content-carousel--docs)             | Embla Carousel — no Base UI primitive            | The scroll track itself is drag/wheel-only, the same tradeoff most carousel implementations make. Only the Previous/Next arrows (Droppy's `IconButton`) are keyboard-operable, each its own ordinary Tab stop. |
| [QuantityStepper](?path=/docs/forms-input-quantitystepper--docs) | Two `Button`s — no dedicated composite primitive | Two ordinary Tab stops, standard Enter/Space per button. The surrounding `role="group"` and the value's `aria-live` announcement are authored directly in Droppy, since Base UI has no dedicated stepper primitive.                                |
