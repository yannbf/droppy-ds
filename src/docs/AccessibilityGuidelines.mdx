# Accessibility guidelines

<Meta title="Accessibility guidelines" tags={['general-a11y']} />

Base UI supplies the behavior underneath every component Droppy ships: ARIA roles and attributes,
keyboard navigation, focus management, pointer interactions. Droppy supplies what sits on top of
that behavior — the focus ring, the contrast, the touch target, the motion — the visible half of
accessibility that a correct ARIA tree alone doesn't cover. This page states the standard both
halves target, how the work divides three ways, and where to find the exact keyboard model for
every composite Droppy ships.

## Standards & targets

Every component targets **WCAG 2.2 Level AA** as the floor, for these groups in particular:

- **Keyboard-only** users, who need a visible focus indicator and a sane tab order on everything
  interactive — no pointer to fall back on.
- **Screen-reader** users, who depend on the roles, names, and states the underlying primitive
  exposes — a component that looks right but announces wrong has failed them regardless of how it
  looks.
- **Low-vision** users, who rely on contrast and scale, often stacked with browser zoom or
  OS-level magnification.
- **Motor-impaired** users, who need targets sized and spaced for imprecise pointing, and no
  interaction that demands split-second timing.
- **Reduced-motion** users, for whom animation is a vestibular or attentional hazard, not just an
  unnecessary flourish.

### Contrast

| Content                                     | Minimum ratio |
| :------------------------------------------ | :------------ |
| Normal text                                 | 4.5:1         |
| Large text (≥24px, or ≥19px bold)           | 3:1           |
| UI component boundaries & graphical objects | 3:1           |

These are the WCAG 2.2 AA numbers (SC 1.4.3, SC 1.4.11) — the floor every token pairing Droppy
ships (text on surface, icon on fill, border on background) targets, in both themes.
[Base UI's own documentation](https://base-ui.com/react/handbook) recommends measuring contrast
with APCA rather than the WCAG ratio alone; unlike the WCAG formula, APCA weighs font size and
weight into the perceived result, so it's the sharper tool for judging anything borderline. Treat
the ratios above as the enforced minimum — automated on every story, see Tooling & workflow below
— and APCA as the better call when a pairing is close.

## The layered contract

Accessibility here is a three-way split, not a single owner.

**Base UI supplies the behavior, and Droppy builds on it.** Most interactive composites wrap a
Base UI primitive, and that primitive is where the ARIA roles and attributes, keyboard navigation,
focus management, and pointer interactions come from — `Tabs` renders
`role="tablist"`/`role="tab"` and roves focus with arrow keys because `@base-ui/react/tabs` does;
`Modal` traps focus and closes on Escape because `@base-ui/react/dialog` does. Droppy doesn't
reimplement any of that. A few composites deliberately sit outside this pattern — see Keyboard
navigation below for which ones, and what stands in for Base UI there.

**Droppy supplies the visible layer** — the part a screen reader has no opinion about, but a
sighted, low-vision, or motor-impaired person is relying on:

- **The focus ring** is one shared design decision, not a per-component choice: `--ds-shadow-focus`
  stacks a 1px inner ring in `--ds-color-focus-ring` with a 4px outer halo in
  `--ds-color-focus-halo` (the inner ring widens to 2px in dark mode), applied on `:focus-visible`
  across every themed interactive part — buttons, form controls, tabs, accordion triggers, toolbar
  items, and more.
- **Color contrast** of every token pairing, to the ratios above.
- **Touch-target sizing.** WCAG 2.2's own floor (SC 2.5.8) is 24×24 CSS px; Droppy aims well past
  it — `IconButton` ships at 4rem (64px) square by default, with a 3rem (48px) `small` variant for
  denser layouts, and `Button`'s padding scale keeps label and icon-only buttons in the same
  comfortable range.
- **Motion that respects the animation doctrine** (full doctrine:
  [Technical guidelines](?path=/docs/technical-guidelines--docs)) — with one open gap: the shared
  theme stylesheet has no `prefers-reduced-motion` rule of its own today. `Skeleton` and `Spinner`
  each implement reduced motion per component; any other motion Droppy or the app layers on top
  still needs something to check that preference.

**The consuming app still owns** page heading structure and landmark order, labels and alt text
for content it provides, reduced-motion respect for animation it drives itself, and form error
text — Droppy reserves the space and the styling hook, the app supplies the message.

## Keyboard navigation of composite components

Base UI's own composites share one model: one Tab stop for the whole widget, arrow keys move a
roving highlight among its members, and a separate activation is sometimes required rather than
implied by focus alone. Every Droppy composite that wraps one of those primitives inherits that
model unmodified. Three composites don't wrap a Base UI composite at all, deliberately — their
keyboard model comes from somewhere else, noted below.

| Component                                                        | Built on                                         | Model                                                                                                                                                                                                                                              |
| :--------------------------------------------------------------- | :----------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Tabs](?path=/docs/navigation-tabs--docs)                        | `@base-ui/react/tabs`                            | One Tab stop for the tablist; arrow keys move a roving highlight and wrap at the ends. A separate activation — click, Enter, or Space — selects; arrow-key focus alone doesn't.                                                                    |
| [Accordion](?path=/docs/layout-structure-accordion--docs)        | `@base-ui/react/accordion`                       | No roving focus, matching Base UI's own alignment with the current WAI-ARIA APG accordion pattern. Every trigger is its own ordinary Tab stop; Enter/Space toggles it.                                                                             |
| [Modal](?path=/docs/overlays-modal--docs)                        | `@base-ui/react/dialog`                          | Focus-trapped popup: Tab/Shift+Tab loop inside it rather than escaping to the page. Escape closes.                                                                                                                                                 |
| [Sidebar](?path=/docs/overlays-sidebar--docs)                    | `@base-ui/react/drawer`                          | Same focus-trap model as Modal. Swipe-to-dismiss is pointer-only, so Escape and the visible close button are the keyboard equivalents.                                                                                                             |
| [Toast](?path=/docs/feedback-status-toast--docs)                 | `@base-ui/react/toast`                           | Outside the page's tab order until summoned: F6 jumps focus to the stack, Tab enters at the newest toast, Escape dismisses the focused one.                                                                                                        |
| [Tooltip](?path=/docs/overlays-tooltip--docs)                    | `@base-ui/react/tooltip`                         | Opens on trigger focus with no delay, closes on blur or Escape. Carries no ARIA relationship to the trigger, so the trigger needs its own accessible name regardless.                                                                              |
| [NumberField](?path=/docs/forms-input-numberfield--docs)         | `@base-ui/react/number-field`                    | Up/Down arrow steps the value; Home/End jump to `min`/`max` when set; typing replaces it directly.                                                                                                                                                 |
| [ScrollArea](?path=/docs/layout-structure-scrollarea--docs)      | `@base-ui/react/scroll-area`                     | Arrow keys and Page Up/Down scroll the focused viewport; the scrollbar thumb itself is never a Tab stop.                                                                                                                                           |
| [Select](?path=/docs/forms-input-select--docs)                   | Native `<select>` — no Base UI primitive         | The platform's own picker, chosen deliberately over a scripted listbox: Up/Down/Home/End and native typeahead once open, Enter/Escape to commit or cancel.                                                                                         |
| [Carousel](?path=/docs/media-content-carousel--docs)             | Embla Carousel — no Base UI primitive            | The scroll track itself is drag/wheel-only, the same tradeoff most carousel implementations make. Only the Previous/Next arrows (Droppy's `IconButton`, itself built on Base UI's `Button`) are keyboard-operable, each its own ordinary Tab stop. |
| [QuantityStepper](?path=/docs/forms-input-quantitystepper--docs) | Two `Button`s — no dedicated composite primitive | Two ordinary Tab stops, standard Enter/Space per button. The surrounding `role="group"` and the value's `aria-live` announcement are authored directly in Droppy, since Base UI has no dedicated stepper primitive.                                |

## Tooling & workflow

`@storybook/addon-a11y` runs on every story — a workspace-wide addon, not an opt-in per component
— and `a11y: { test: 'error' }` in `.storybook/preview.tsx` means an axe violation fails the story
outright, rather than just flagging it in the Accessibility panel.

`@storybook/addon-vitest` turns every story into a browser test, run through Playwright's
Chromium. The same `test: 'error'` setting applies there too: a component that fails its
accessibility check fails the test run, not just the visual review. There's nothing to hand-write
for this — the assertion comes from the addon wiring itself, not a call inside a test file.

Automated coverage has a shape: axe catches missing labels, bad contrast, and invalid ARIA, not
whether the tab order makes sense or a screen reader announces a state change usefully. Give every
new component — especially one that isn't wrapping a Base UI primitive — a manual keyboard pass
and a screen-reader smoke test before it ships.

When a rule genuinely needs to be relaxed for a deliberate design choice, document why at the
point of the override — the way `Carousel`'s story disables the `color-contrast` rule for its
intentionally dimmed, non-interactive slide previews, with a comment explaining the exception
rather than a silent rule change.
